## Баги этой сессии — все найдены и пофикшены

### 1. Встроенный YMapZoomControl (+/-) был сломан той же болезнью v3, что и
всё остальное

Клик на "+" анимированно доезжал ЧАСТИЧНО (например zoom 6 → 6.95, не до 7) и
дальше ВСЕ следующие клики становились no-op навсегда — тот самый баг
анимированного `setLocation` из предыдущих хендоверов, просто теперь он же
сидел и во встроенном контроле, о чём никто раньше не догадался проверить.

**Фикс, а потом ещё одно решение поверх фикса**: сначала заменил
`YMapZoomControl` на свои `+`/`-` кнопки с safe-паттерном `duration:0`
(коммит `189834d`) — работало отлично, протестировано (5 кликов подряд дали
ровно 6→7→8→9→8→7→6, без сбоев). Но юзер в итоге попросила **убрать
+/- контрол вообще** (коммит `892ab73`) — зум остался только через pinch на
мобильном и колесо мыши на десктопе (`behaviors:['drag','pinchZoom',
'scrollZoom','multiTouch']` у `YMap`, без `'dblClick'`).

### 2. Зум по двойному тапу на карту — отключён

Тот же `behaviors` без `'dblClick'` в конструкторе `YMap`. Юзер явно просила
убрать (мешало при двойном тапе рядом с UI-элементами).

### 3. Попап у пина обрезался/утыкался в край экрана

Два отдельных случая, оба почищены в `openPopup`/`openClusterPopup` через
функцию `clampPopupToViewport(loc)`:

- **Горизонтально**: если recentering в `selectLocation()` не успевал/не
  срабатывал (та же порода багов v3), попап (фиксированная ширина
  440/220px) вылезал за левый/правый край. Чинится через прямой inline
  `transform` (см. ниже — критично: НЕ через CSS-переменную).
- **Вертикально**: попап растёт ВВЕРХ от пина; если пин оказывался слишком
  низко на экране, низ попапа утыкался в нижнюю часть экрана — там же, где
  сидит загадочная посторонняя штука с фото и текстом "Открыть Яндекс
  Карты" (см. раздел «НЕРЕШЁННАЯ ЗАГАДКА» ниже). Фикс — по-настоящему
  пересчитывает центр карты (через формулу метров-на-пиксель Web Mercator)
  так, чтобы пин поднялся выше 58% высоты экрана, и переставляет маркер.
  Визуально проверено скриншотом — работает, хвостик попапа корректно
  остаётся приклеен к пину.

**КРИТИЧНО ВАЖНАЯ находка про CSS**: пробовал сделать горизонтальный сдвиг
через CSS custom property (`--nudge-x`) внутри `calc()` в `transform`.
**Не сработало** — проверено многократно (задавал `--nudge-x: 9999px`,
форсировал reflow через `offsetHeight`, менял через `setProperty` — рассчитанный
`transform: matrix(...)` не менялся вообще, будто переменная не читается,
хотя `background: var(--test-color)` на том же элементе работает нормально).
Похоже на баг рендеринга конкретно для `transform`+`var()`+`calc()` в связке
на этом маркере (возможно из-за того, что YMapMarker сам управляет
позиционированием через compositor/will-change). **Вывод: сдвиги позиции
через `popupEl.style.transform` всегда ставить строкой целиком
(`popupEl.style.transform = 'translate(calc(-50% + ${px}px), ...)'`), не
через CSS-переменную.**

Код фикса — функция `clampPopupToViewport` в `index.html`, вызывается из
`openPopup()` и `openClusterPopup()` через `setTimeout(..., 60)` (не через
`requestAnimationFrame` — в этом Browser-пейне/окружении `rAF`, даже
двойной, не гарантированно фнерится вовремя после `.update()` маркера;
`setTimeout(fn, 60)` — надёжно, проверено).

### 4. Маленькие кластеры (2-3 места по одному адресу) — теперь отдельные иконки

Раньше клик по кластеру из 2-3 мест по одному адресу (типа отель + музей в
одном здании) показывал безликую цифру "2"/"3" в кружке. Юзер попросила
показывать иконки категорий рядом. Сделано (коммит `0c72081`): если
`clusteredFeatures.length <= 3`, вместо `.cluster-dot` рендерится
`.cluster-group` — несколько `.pin` с зазором `gap:6px` (юзер явно попросила
**без нахлёста/overlap**, только зазор), каждая иконка кликабельна
независимо (`stopPropagation()` + свой `selectLocation`). Кластеры от 4 мест
и больше — как раньше, цифра + список по клику.

Протестировано на реальном примере из базы: id 140 «Отель Провинция» +
id 143 «Музей хлеба» в Серпухове, одни координаты — обе иконки кликаются
независимо, открывают свой попап.

## НЕРЕШЁННАЯ ЗАГАДКА — плашка "Открыть Яндекс Карты" с домиком снизу экрана

На мобильном (и в скриншотах юзера с реального iPhone, и в тестах через
Browser-пейн) внизу экрана периодически появляется штука: белая шторка с
ручкой для свайпа, фото домика (совпадает один-в-один с нашим собственным
`images/1.jpg`!) и синей ссылкой "📍 Открыть Яндекс Карты".

**Доказано железно, что это НЕ часть нашей страницы:**
- Текста "Открыть Яндекс Карты" НЕТ нигде в исходнике `index.html`.
- Прошёлся по всему DOM программно, включая обход shadow DOM (у `<ymaps3>`
  веб-компонентов) — ничего похожего не нашлось, кроме крошечной законной
  подписи-атрибуции Яндекса (148×14px, другой текст, другая позиция,
  `class="ymaps3--open-maps-button"` — это реальный маленький `<a>` с
  `href="https://yandex.ru/maps/?...&z=N"`, легитимная и обязательная по
  условиям API вещь, трогать нельзя).
- Спрятал `#map` через `display:none` целиком — штука с домиком **осталась
  на экране**, значит она не рендерится внутри `#map`/нашего кода вообще.
- Единственная теория, что осталась: рендерится в **closed shadow root**
  (туда JS в принципе не может заглянуть) — возможно, часть SDK Яндекса
  (`@yandex/ymaps3-hint` или похожий модуль, всплывал в поиске по npm) — но
  не подтверждено окончательно.

Юзер уже подтвердила (скриншот с кружком), что это **отдельная штука**, а не
наш попап — в тот раз наш собственный попап (с крестиком) был виден РЯДОМ
и НАД этой шторкой, обрезанный ею снизу — именно это и стало причиной
вертикального фикса попапа (баг #3 выше). Сама же загадочная плашка как
была, так и осталась — **это не баг, который можно починить в нашем
`index.html`**. Если юзер снова спросит про неё — не пытайся чинить кодом,
это либо нативная функция мобильного браузера, либо что-то в closed shadow
DOM самого Яндекс SDK, вне нашего контроля.

### Проблема (подтверждена данными)

234 из 245 мест на карте показывают **дублирующиеся фотографии** — всего
39 уникальных фото на 245 записей, некоторые переиспользуются по 10-11 раз
(например гид по 11 японским ресторанам Москвы — все 11 показывают одно и
то же фото).

**Причина** (не баг кода, баг структуры исходных данных): большинство мест
в базе извлечены из постов-подборок в Telegram-канале вида «🔸Ресторан А —
..., 🔸Ресторан Б — ...» — один текстовый пост перечисляет 8-11 заведений, а
прикреплённое к посту фото — **одно на весь пост** (как обложка). Скрипт
`data/extract_locations.py` (строка ~124, `"photos": post["photos"]`)
назначает это единственное фото ВСЕМ местам, извлечённым из поста. Проверено
через `posts.json` (1097 постов всего) — **ни один пост не содержит больше
1 фото**, так что это ограничение исходных данных, не пайплайна.

### Что уже проверено и НЕ сработало

Первым делом (по просьбе юзера) проверил, нет ли в локальном архиве

каждое место — прогнал все 245 названий по всем 1097 постам в поиске
совпадений. Результат: **нашлось буквально одно случайное совпадение, и то
сомнительное** (не про то место). То есть локально достать нечего — надо

## Прочие грабли инструментов (актуальны и сейчас)

- Долгоживущие вкладки Browser-пейна накапливают битое состояние — при
  странном поведении сначала открой свежую вкладку.
- `computer{action:"left_click"/"double_click"}` часто таймаутится на 30
  сек без видимой причины. Это НЕ значит, что клик не прошёл — иногда
  проходит, иногда нет. Для надёжного тестирования интерактивности лучше
  дёргать функции напрямую через `javascript_exec` (временно вешая
  `window.__debugXxx = xxx` на нужные функции/карту, и ОБЯЗАТЕЛЬНО убирая
  перед финальным коммитом — грепни `__debug` перед `git add`).
- `computer{action:"zoom"}` с обрезкой региона не поддерживается в этом
  Browser-пейне, возвращает полный скриншот.
- Для видео от юзера — `ffmpeg` может быть не установлен (`brew install
  ffmpeg`, ставится за секунды, доступен).
